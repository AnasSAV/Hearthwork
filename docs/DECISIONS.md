# Decisions

Judgement calls and places where the brief and the real libraries didn't match. Newest at the bottom.

## Phase 0/1 (2026-10-23)

### Library versions (checked on npm, 2026-10-23)

- **Phaser 4.2.1**. The v4 migration guide (shipped in `node_modules/phaser/changelog/v4/4.0/`)
  says tilemaps, sprites, input, cameras and tweens are unchanged. `roundPixels` now defaults to
  `false`, so we set it to `true` next to `pixelArt: true`.
- **Colyseus 0.18** server (`colyseus` meta package) and **`@colyseus/sdk` 0.18** client.
  `colyseus.js` is the old SDK name; don't use it. Schema is **v5**.
  - State is defined with the decorator-free `schema({...})` builder, so there are no
    `experimentalDecorators`/`useDefineForClassFields` tsconfig flags, and the classes live in
    `shared/` where both sides import them.
  - Client listens with `Callbacks.get(room).onAdd/onRemove/onChange/listen` (the 0.17+ API;
    `room.state.players.onAdd` is gone).
  - Server: `defineServer({ rooms: { town: defineRoom(TownRoom) } })` + `listen()`.
  - Reconnection: the SDK auto-reconnects; the server keeps the seat in `onDrop` via
    `allowReconnection(client, 20)`. If the server itself restarted, the client gets `onLeave`
    and the Town scene restarts and joins a fresh room.
  - Closing or reloading a tab must not leave a ghost for 20 s. The client sends a consented
    `room.leave()` on `pagehide`. As a backstop the server skips the grace period when the
    socket closes with 1001 "going away" (browser tab close/navigation). Real network drops
    (usually 1006) still get the grace period, and others see that player dimmed with "(away)".
- **TypeScript 6.0.x, not 7.0**. TS 7 (the native port) is `latest` on npm, but
  `typescript-eslint` 8.x only supports `<6.1`. Revisit when typescript-eslint supports 7.
- **Vite 7.3, not 8**. Vite 8 bundles with rolldown, whose native `.node` binding is blocked by
  Windows Smart App Control on the dev machine ("An Application Control policy has blocked this
  file"), and its WASI fallback can't resolve Windows drive paths. Vite 7 (Rollup + esbuild)
  works. Revisit if Smart App Control is disabled or rolldown's binary gets signed.
- **Zod 4**, React 19, Vitest 5.

### Validation

- Colyseus 0.18 can validate messages itself (`onMessage(type, zodSchema, handler)`), but on
  failure it **disconnects** the client. The brief says "reject and log", so
  `server/src/rooms/validated.ts` wraps handlers with `safeParse`: invalid payloads are logged
  and dropped, and the client stays connected. A `'*'` handler logs unknown message types.

### Movement

- Positions are the point between the player's feet. Collision uses a 10×6 px feet box against
  the Tiled `collision` layer (any non-empty tile is solid). The same `shared/movement.ts` code
  runs on the client (prediction) and the server (validation).
- Client sends `move {x, y, dir, moving}` at most every 100 ms, only when something changed.
  The server drops messages <50 ms apart, checks speed (80 px/s × 1.3 tolerance + 4 px, crediting
  at most 500 ms of elapsed time so idling can't bank a teleport), and checks the straight or
  axis-first path for walls. On rejection it sends `move:correct` and the client snaps back.
- Collision is our own tile check, not Arcade Physics, so client and server agree exactly.

### Map and art

- Town map (48×36 tiles) used Kenney **Tiny Town** (terrain, buildings, trees) and **Roguelike
  Indoors** (desks, tables, chairs); characters came from Kenney **RPG Urban Pack**. All of it
  was replaced by LimeZu art after Phase 5 (see the LimeZu sections below).
- The map was generated by `tools/maps/build-town.ts` (both `.tmx` and `.json`) as a
  starting point (replaced by `tools/art/build_town.py` in the LimeZu conversion, below).
- Anything that looks like an obstacle is solid, including mushrooms and sprouts (they started
  on the walkable `decor` layer, which confused playtesters). `decor` is reserved for things
  you can walk over.
- Map layers: `ground`, `decor`, `buildings` (visible), `collision` (hidden), `objects`
  (`spawn` point, `desk` seats with `facing` and an optional `table` for group focus, `building`
  with door coordinates, `plot` with `plotIndex` 0–5 for Phase 4 houses).
- The server imports `town.json` at build time (esbuild/tsx bundle it), so it never reads map
  files from disk at runtime (Render wipes the filesystem).

### Identity in Phase 1

- No accounts yet: each tab gets a guest name/avatar (sessionStorage, overridable with
  `?name=Alice&avatar=2`), validated by Zod in `onAuth`. Phase 2 replaces this with Supabase
  JWT verification.

### Misc

- `shared/` is consumed as TypeScript source (no build step). Vite compiles it for the client;
  esbuild bundles it into `server/dist/index.js`.
- React `<StrictMode>` is off because its dev double-mount would boot Phaser and join the room
  twice.
- Dev builds expose `window.__game` for debugging and browser tests. Production builds strip it.

## Phase 2 (2026-10-23)

### Auth

- The game server verifies the Supabase access token with `supabase.auth.getClaims(token)`
  (supabase-js 2.118). It checks locally against the project's JWKS when asymmetric JWT signing
  keys are on (Supabase's recommendation), and asks the Auth server for legacy shared-secret
  projects. So no JWT secret is needed in `server/.env`.
- The client sets `colyseus.auth.token = <access token>` before `joinOrCreate`; Colyseus 0.18
  delivers it to `onAuth(client, options, context)` as `context.token`. A fresh token is read
  from Supabase on every join attempt (tokens expire hourly).
- Keys: Supabase's new **publishable** (`sb_publishable_…`) and **secret** (`sb_secret_…`) keys
  work in the same slots as the legacy `anon` / `service_role` keys. Env names stay
  `VITE_SUPABASE_ANON_KEY` / `SUPABASE_SERVICE_ROLE_KEY` to match the brief.
- Signup creates the profile with a placeholder username (`player_<id>`) and empty avatar,
  because Google sign-ins have no username yet. The client shows the username/avatar picker
  until a valid avatar is set (v2 since the LimeZu characters, see below). `update_profile()` is the only way players change their profile
  (no direct UPDATE privilege), and joins are refused until the profile is complete.
- Usernames: `^[A-Za-z0-9_]{3,16}$`, unique case-insensitively.
- One account can be in town from several tabs (useful for testing), but only one focus
  session per user exists. Starting one ends the other with reason `replaced`.

### Database

- Privileges are stricter than the brief's minimum: players and even the service role have
  only SELECT on game tables. All writes go through `SECURITY DEFINER` functions with
  `search_path = ''`, and EXECUTE is revoked from PUBLIC/anon/authenticated and granted
  per function. `coin_ledger` is append-only (no UPDATE/DELETE grants).
- Extra table `focus_daily (user_id, day, minutes, coin_minutes, coins)` tracks the daily coin
  cap. It will also power the streak calendar.
- Extra functions: `start_focus_session`, `end_focus_session`, `abandon_active_sessions`
  (server startup), `ledger_mismatches` (invariant check).
- A partial unique index guarantees one `active` focus session per user at the database level.
- `house_levels` rows are inserted by the migration, not `seed.sql`, because the signup
  trigger's level-1 house needs them to exist. Plot assignment takes the lowest free
  `plot_index` under an advisory lock.
- `award_focus(user, session, minutes, bonus, base_rate, streak_step, streak_max, daily_cap)`:
  the extra parameters (with defaults matching the brief) are passed from
  `shared/src/constants.ts`, so the constants stay single-sourced. It only accepts sessions
  that are still `active` and belong to the user.

### Economy rules (interpretation)

- "Today" is the **UTC** day for both the daily cap and streaks. A per-user timezone would be
  nicer, but a client-supplied timezone could be abused to reset the cap early.
- `streakDays` counts consecutive UTC days with focus **including today**, so the first day
  already gets ×1.05 and the multiplier caps at ×1.5 from day 10.
- Coins per award chunk are `round()`ed (half up). With 5-minute chunks that means 5.25→5,
  12.5→13, so the rounding roughly evens out.
- The completion bonus is not limited by the daily cap (it's small).
- A 25/50-minute block is complete when that many minutes are **verified** (not wall-clock).
  The on-screen countdown jumps back when a minute doesn't count, and says why.
- Session status: `completed` = block finished, or an open-ended session the player ended
  themselves; `abandoned` = ended early, replaced, missed beats, disconnected or server
  restart. Verified minutes are paid either way.
- "Still here?" appears after every 25 verified minutes (not wall-clock), except when a 25-min
  block just finished. While it's open, no minute counts.
- Beats: on time = 50–80 s after the previous one. 3 missed beats (about 3½ min of silence) end
  the session. Verified minutes never exceed elapsed minutes.
- Players are seated at the desk while focusing: the server snaps them to the chair and rejects
  moves until the session ends. Disconnecting (after the reconnect grace period) ends it.
- The client sends beats from a Web Worker timer because browsers throttle background-tab
  timers (Chrome: once per minute after 5 minutes hidden), which would make audio-only beats
  late.
- Server restarts lose the in-memory trackers. On startup the server marks leftover `active`
  rows abandoned (single-process assumption, true on Render and one VM). At most 4 unsaved
  verified minutes per session are lost.

### Not in Phase 2

- Group focus tables (shared Pomodoro at the same table) are in the Multiplayer section of the
  brief but not in any phase's checklist. The map already tags group-table seats with `table`.
  Planned for Phase 5 polish unless you want it sooner.

### Testing

- `npm run test:db` runs SQL integration tests against a local Supabase stack (Docker).
  `npm run e2e:focus` runs a real-time 6½-minute focus session through the real server.

## Phase 3 (2026-10-23)

### Catalog

- 50 items (22 furniture, 18 decor, 4 plants, 3 wallpapers, 3 floors) from Kenney Roguelike
  Indoors plus a few Tiny Town plants/walls. `shared/src/catalog.ts` is the single source and
  `npm run seed:items` generates `supabase/seed.sql` from it. A unit test fails if they drift.
  At runtime the `items` table is authoritative: the shop reads prices from it and `buy_item`
  charges from it.
- `items.sprite_key` is self-describing, `sheet:x,y,w,h` (tile rectangle in a tileset), so the
  client can draw any item without a separate atlas. The rectangle size is the footprint.
- Extra `items` columns: `surface_host` (tables, desks, dressers can hold `surface` items like
  candelabras, for Phase 4's `canPlace`) and `active` (retired items stay for inventories but
  leave the shop).
- Categories follow the brief (`furniture | wall | floor | decor | plant`). `wall`/`floor` are
  wallpapers and floorings that restyle the room. Hung decor (paintings, shields) is category
  `decor` with layer `wall`. Rugs are `decor` with layer `rug` and cost 90–120: they're big, so
  they sit above the 40–80 "small decor" band.
- Level gates: long dining table, piano and the two big couches need house level 2; the
  gilded mirror needs level 3.

### Buying

- `buy_item(item_id, request_id)` is called straight from the browser (as the brief says),
  with the player's JWT. The client sends only the item id plus a fresh UUID per click. The
  function locks the profile row, so concurrent purchases by one player run one at a time,
  reads the price from `items`, and checks house level and balance. It then writes the coin
  change, a `purchase` ledger row (ref = purchase id), a `purchases` row and the inventory
  increment in one transaction.
- Double-clicks: the button disables while a purchase is in flight (with a ref guard for clicks
  that land before re-render). A repeated `request_id` returns the original result without
  charging. Five simultaneous buys with coins for one buy exactly one (tested).
- Wallpapers and floors can only be bought once.
- The HUD balance updates from `buy_item`'s returned balance. Focus awards still come from the
  game server.

### Dev tooling

- `client/vite.config.ts` adds `shared/src` to Vite's file watcher: it's outside the Vite root,
  so without this, edits to `shared/` were served stale until Vite restarted.
- Dev builds expose `window.__supabase` so RLS can be poked from the browser console.

## Phase 4 (2026-10-23)

### Geometry

- Each room is the `house_levels` grid (L1 8×6, L2 12×8, L3 12×8 × 2 rooms). Row 0 is the wall
  row; `wall`-layer items only go there and must be 1 tile tall. Rows 1..h-1 are floor.
- The front door is under floor tile (width/2, height-1) of room 0. Two-room houses connect at
  row height/2. Floor items may not cover those doorway tiles (so nobody gets boxed in), but
  rugs may.
- Upgrades keep coordinates, so furniture stays put and new space appears right/bottom, as the
  brief asks.
- The interior world adds a 1-tile outer wall all round, a wall column between rooms and an
  exit mat in the bottom wall. Walking onto the mat leaves the house (no key press needed).
- **Rotation is stored but must be 0.** The pixel-art sprites have no rotated versions;
  `save_layout` and `canPlace` reject anything else for now.

### Placement rules (`canPlace` in `shared/src/house.ts`, re-checked by `save_layout` in SQL)

- In bounds and on the right row for the layer. No overlap within a layer: rugs under
  furniture are fine, two rugs are not. `surface` items need a `surface_host` table/desk under
  every tile.
- No wallpapers/floors as placed items, no rooms the house doesn't have, and level-gated items
  need the level.
- Ownership: you can place at most as many copies as `inventory.qty`. Placing doesn't consume
  inventory; it's "owned total". Picking up just removes the placement, so nothing is
  destroyed. Lifting a table also returns anything standing on it.
- A DB test feeds 25 random layouts through both `validateLayout()` (TypeScript) and
  `save_layout` (SQL) and requires identical accept/reject results.

### Editing

- The owner presses **Decorate**. The layout is edited locally (React drawer plus Phaser
  ghost); nothing hits the database until **Save layout**, which calls `save_layout` (one
  transaction, replaces all `placed_items`). The house room is then told to reload, and
  everyone inside sees the new layout. Cancel throws the draft away.
- The ghost shows the item sprite over a green or red footprint (a multiply tint alone was
  unreadable on green items). Drag from the drawer, or click an item then click a spot.
  Click placed furniture to pick it up; right-click/Esc returns the carried item.

### Rooms

- `house` rooms are `filterBy(['ownerId'])`: one per owner, created by the first visitor
  (owner included), disposed when empty, rebuilt from Postgres every time.
- `onAuth` checks `can_visit(visitor, owner)` (public / friends / private). If the owner
  tightens visibility while friends are inside, they get a notice and are sent back to town.
- Studying in a house: the floor tile below each desk/table (`items.study_spot`) is a seat;
  focus sessions there are identical to town desks (same `FocusController`, same `award_focus`),
  so visitors earn coins at a friend's desk.
- Players are pushed to the doorway if a layout change leaves them inside furniture; sessions
  at a removed desk end.

### Town lots

- The town map has 6 lots; houses with `plot_index` 0–5 appear there with level- and
  style-based exteriors (L1 3 tiles wide, L2 4, L3 5 with a chimney; cottage = blue roof and
  timber, brick = red roof and stone). Lots are solid in the collision layer; the door tile's
  doorstep is the interaction point. Empty lots show "For sale".
- **Players beyond plot 5 have no lot yet.** They reach their house with the HUD's **Home**
  button and friends' houses from the Friends panel. More lots or neighbourhood streets can
  come later.
- Town rooms reload lots every minute and immediately when a shown house changes (an
  in-process event from the house room, single-process deployment).

### Friends

- One `friendships` row per pair (enforced by a unique index on the unordered pair): `pending`
  means `user_id` asked `friend_id`; accepting flips it to `accepted`. Asking someone who
  already asked you accepts. `my_friends()` (security definer) returns usernames/avatars, since
  profiles are otherwise private to their owner.

### Client structure

- `WorldScene` is the shared base (players, prediction, focus messages, reconnects, zoom);
  `TownScene` and `HouseScene` extend it. Switching worlds stops one scene (leaving its room)
  and starts the other. Leaving a room ends a running focus session, with verified minutes
  paid as usual.
- The brief's `HouseEdit` scene became an edit mode inside `HouseScene` (same scene, same
  room), driven by `client/src/house/editor.ts`.

## Phase 5 (2026-10-23)

### Chat

- Room-scoped (town instance or house). The server trims, strips control and zero-width
  characters, caps at 200 chars, masks profanity (`shared/src/chat.ts`, a small English list
  with l33t and repeated-letter matching and Scunthorpe-safe word boundaries), and allows one
  message per second (extra ones get a "slow down" notice rather than a disconnect).
- The last 50 messages stay in room memory; newcomers get the last 20. **Reports** carry only a
  message id: the server looks up its own copy and stores it in `chat_reports` (service role),
  so nobody can report words that were never said. Review open reports in the SQL editor:
  `select * from chat_reports where not resolved order by created_at desc`.
- **Mute** is per viewer and stored in the browser (localStorage), by user id. Muted players'
  messages and speech bubbles are hidden.
- While any text field has focus, Phaser's keyboard is disabled (it captured W/A/S/D/E/I
  globally, which also broke the Friends search box).

### Group focus tables

- The two plaza tables (`table` property on their seats in the map) share one Pomodoro. The
  first person to sit picks 25 or 50 minutes (open-ended isn't offered there); later arrivals
  join the same countdown, synced as `TownState.tables`. Each person's minutes are still
  verified individually. Late joiners can't finish the whole block, so they get no completion
  bonus. The table closes 90 s after the countdown (grace for the last heartbeat), and empty
  tables reset.
- Clients need the server's clock for countdowns, so rooms send `clock` on join and every
  30 s.

### Radio and ambience

- The brief's mechanism is followed exactly: `client/public/radio/playlist.json` has tracks and
  durations plus `startedAt`; every client computes `(serverNow - startedAt) mod
playlistLength` (`shared/src/radio.ts`, unit-tested) and plays that track from that offset.
- **No music files are shipped**: there were no license-cleared lofi tracks to bundle. The
  default tracks are `synth:<seed>`: deterministic lofi generated in the browser with WebAudio
  (chords, bass, swung drums, melody, vinyl crackle), identical for everyone, CC0 by
  construction. To add real tracks, drop license-cleared files in `client/public/radio/` and
  list them with `src`, `durationSec` and `license`; both kinds can be mixed.
- Ambient rain, fireplace, birds and wind are synthesised too, with a per-player mix saved in
  the browser.
- Audio starts on a click (browser autoplay rules). Playing audio also keeps background tabs
  from being throttled, which pairs well with the focus timer's audio-only mode.

### Stats

- A **Stats** panel (in-game modal rather than a separate page) shows totals, current and
  longest streak, best day, sessions, coins earned/spent, a 14-day bar chart and a 26-week
  streak calendar. One SQL function, `my_stats()`, does the aggregates; `focus_daily` feeds the
  charts. Charts follow the dataviz rules: one sequential blue ramp stepped for the dark
  surface, a hover tooltip on every mark and a table view.
- Streaks shown anywhere (HUD, stats) are the _effective_ streak: zero if the last focus day
  was before yesterday (UTC). Previously the HUD showed a stale stored value.

### Operations

- `npm run check:ledger` (and the nightly workflow) fails if any balance differs from its ledger.
- `npm run load -- --bots N --seconds S` runs signed-in bots with legal movement and chat. On
  the dev machine: 30 bots, join p50/p95 36/53 ms, 7,773 moves with 0 server corrections, chat
  delivered to all 30.
- Deploy files: `render.yaml`, `deploy/pm2/ecosystem.config.cjs` (one fork-mode instance),
  `deploy/caddy/Caddyfile`, `client/public/_headers`, `.node-version`, and workflows for CI,
  keep-alive, encrypted nightly `supabase db dump` and the ledger check. Walkthrough:
  `docs/DEPLOY.md`.
- Production builds run on Node 22 (Render, Pages, CI); development used Node 24.

## After Phase 5 (2026-10-23)

### Private chat (whispers)

- A whisper is a 1-to-1 private conversation with someone **within 4 tiles** (64 px). Click a
  nearby player (or pick them under "Nearby" in the chat) to open a 🔒 tab. Only the two
  players receive the messages (no speech bubble, not in room history).
- Range is checked by the server on every message (with 16 px slack for movement). If you
  walk apart, the conversation stays visible but the input is disabled until you're close
  again.
- Whispers share the chat rate limit and profanity filter. Mute hides a player's whispers too.
  Whispers can be reported by their recipient only; reports are stored from the server's copy.
- Conversations are per room (session ids change between rooms) and clear when you leave.

### LimeZu art, stage 1: characters

- Art style: LimeZu **Modern Interiors + Modern Exteriors** (paid, credit required, no
  redistribution of the packs). The source packs stay outside the repo; `tools/art/` scripts
  read them and write only small derived atlases into `client/public/assets/`.
- Characters come from the Modern Interiors character generator (16×32 frames): body (skin),
  eyes, outfit, hair and an optional accessory. `tools/art/build_characters.py` keeps the idle,
  walk and sit rows, packs one atlas per part (`assets/characters/*.png`) and generates
  `shared/src/avatarParts.ts` (ids + swatch colours). Kids' bodies and premade characters are
  not used.
- An avatar is `{ v: 2, body, eyes, outfit, hair, acc }` part indices (acc −1 = none).
  `update_profile` range-checks each index (a unit test keeps the SQL ranges in step with the
  manifest), so the manifest must only ever be appended to. Old `{ body }` avatars stay in the
  database; those players see "Meet the new you" and make a character before joining.
- `PlayerState.avatar` is a compact string (`"1.0.12.40.-1"`). The client composites each
  distinct avatar once into a canvas sprite sheet with idle (breathing) and walk animations;
  the UI draws the same parts as stacked CSS backgrounds.
- Players can change their name and character in game ("Character" in the HUD). The client
  saves through `update_profile`, then sends `profile:reload`; the server re-reads the profile
  from the database (2 s cooldown) and updates the synced name and avatar.

### LimeZu art, stage 2: the town

- `tools/art/build_town.py` (`npm run map:town -- <pack path>`) builds the town from Modern
  Exteriors singles: it cuts every piece it uses into one deduplicated tileset
  (`tilesets/town.png`), lays out the map and writes `town.json` + `town.tmx`. It replaces the
  Kenney `tools/maps/build-town.ts`. Tiled edits take over once the map is hand-tuned.
- The town grew to 68×50 tiles to fit LimeZu's scale: Library (Victorian house), Furniture Shop
  (hardware store), a clock tower, a paved plaza with a fountain and two tree planters, six lots
  on a street to the south, and a forest border.
- New layers: `ground`, `paths`, `decor` (walkable), `below`/`below2` (lower parts of objects,
  under players), `above`/`above2` (tree tops, lamp heads, over players), `collision`.
  Tall objects are split: their bottom rows are solid and drawn under players, their upper rows
  are drawn over players, so people can walk behind trees.
- Seats are side-facing chairs at outdoor tables (seats `facing` left/right). LimeZu only has
  side-on sitting frames, so a focusing player in a left/right seat plays the sit animation.
  Two group tables have 6 seats each (3 tables in a column); four 2-seat tables are solo desks.
  20 seats in total (was 18).
- House exteriors come from Modern Exteriors' small/medium/big cabins (6, 8, 10 tiles wide) for
  levels 1–3, drawn from `sprites/houses.png` (Phaser atlas). Every size has its door in column
  2, so a lot's doorstep never moves when the house grows. Style values stay `cottage`/`brick`
  in the database; the UI calls them "Classic" (glass windows) and "Shutters".
- Houses are sorted by their bottom edge like players; map layers sit below and the above layers
  over everything (`client/src/game/depths.ts`).

### LimeZu art, stage 3: interiors and the catalog

- `tools/art/build_interiors.py` packs one Modern Interiors sprite per catalog item into
  `tilesets/furniture.png`, the wall/floor styles into `tilesets/room.png`, and generates
  `shared/src/interiorSprites.ts`. The Kenney sheets (`tinytown.png`, `indoor.png`) and our
  `house.png` are gone.
- All 50 item ids, categories, layers and prices are unchanged so inventories, purchases and
  layouts stay valid. Names follow the new art (e.g. `cabinet_potions` is now a "Wardrobe",
  `candelabra_*` are table lamps); the seed upserts them.
- Items now have a footprint (`size`, = `items.footprint_w/h`) separate from the sprite. A sprite
  is as wide as the footprint and may be taller; it is drawn bottom-aligned so bookshelves, beds
  and pianos rise in front of the wall. Some footprints changed (rugs are 2×2, beds 2×2, sofas
  one row deep); `save_layout` reads footprints from the items table, so no SQL change was needed.
  A layout saved with old footprints still renders; it is re-validated on the next save.
- Walls are drawn two tiles tall: the logical wall row plus the border row above it, so wall
  items (1×1 footprint, 1×2 sprite) reach up the wall. The geometry (and `save_layout`) is
  unchanged. Walls repeat the middle column of a Room Builder block (its outer columns are end
  pieces); floors repeat the whole 3×2 block.

## Homes, housemates and the world map (2026-10-23)

### Homes and housemates

- Everyone still owns a house (created at signup). `profiles.home_owner` says where a player
  lives: null = their own house, otherwise the owner of a friend's house they moved into.
  Members of a home are its owner (if they live there) and everyone pointing at it; up to 4.
- Moving in needs both sides: a player asks (`request_move_in`, also offered on the first-run
  "Where will you live?" screen) and someone in the household accepts, or a member invites a
  friend (`invite_housemate`) who accepts (`respond_house_invite`). Housemates become friends.
  `leave_home` moves back home; the owner can `remove_housemate`. One level only: you can't
  move in with someone while people live in your own house.
- Coins and inventories stay personal. `placed_items.placed_by` records whose inventory an item
  came from. Any member can move or remove anyone's items, but only adds their own; a player's
  placed items only ever exist in their current home (moving in or out returns them to the
  inventory, which counts owned items, not unplaced ones). Wallpaper/floor: keep the current
  one or use your own. Any member can upgrade (the caller pays) and change settings.
- Visiting a friends-only home: friends of any member may come in. The friends list's Visit
  goes to where a friend lives.
- Players start at home, on the doorstep (`at: 'door'`); arrivals from town or the map come in
  at the garden gate.

### Yard and garden

- Each home is one world: the yard (a fenced 20×14 garden with the house exterior at the top,
  a path from the door down and across to a gate, and a "Town" signpost) on the left, the
  interior on the right. Walking up into the front door or onto the exit mat sends
  `house:door`; the server checks the player is at the door and moves them (no free teleports).
  Walking out of the gate goes to town. The camera frames whichever part you are in.
- The yard is layout room -1. A new `garden` category (17 items: trees, bushes, hedges,
  flower beds, benches, a garden table you can study at, lamp, fountain, BBQ…) only goes in the
  yard, and nothing else does. The house, the paths and the signpost are kept clear; the SQL
  mirrors `YARD_RESERVED`. The catalog now has 50 indoor items (the brief's 30–50) plus the
  garden items.

### The town and the map

- The town no longer shows houses (and lots are gone; `houses.plot_index` is still assigned at
  signup but unused). It is the shared study hub: the plaza (2 group tables, 8 solo seats), a
  café terrace (a 6-seat group table), a park reading garden (4 solo seats) and a pond with
  fish, a promenade with lamps, flower beds, benches, and flags by the library. Animated
  pieces are `anim` objects in the map, played from `sprites/town-anims.png`. 30 seats.
- The world map (HUD "Map" or **M**) shows the town, your home, friends' homes you may visit
  and public homes (`world_map()`, at most 60), as a ring around a picture of the town; homes
  whose owner moved in elsewhere are left off. Pick one to travel there.

## Interface redesign, widgets and a living world (2026-10-24)

### Look and feel

- A cozy paper-and-wood interface: cream panels with a wooden lift, chunky pressable buttons,
  rounded **Nunito** for text and numbers and **Pixelify Sans** for titles (Google Fonts, SIL
  OFL). Icons are hand-drawn 12×12 pixel masks (`client/src/ui/Icon.tsx`) rather than an icon
  font, so they match the pixel art. Panels pop in, drawers slide, hints bob.
- HUD: a player card (avatar, coins that count up with a "+N" float, streak, people focusing)
  and an icon toolbar with tooltips. The old "Sounds" button became a music player bar.
- Little synthesized UI sounds (click, open, coin, pop, whoosh, chime), with their own volume.
- Name tags and speech bubbles are drawn as rounded pills; players have a soft shadow.

### Chat and emotes

- Chat collapses to a launcher with the last messages peeking as bubbles; open, it shows
  message bubbles with coloured initials, whisper tabs and a Nearby row.
- Emotes: number keys 1–0 (or the smile button) pop one of 10 LimeZu emote bubbles over your
  head for everyone (`emote` message, server rate-limited to one per 1.2 s). Typing shows a
  "…" bubble (`typing` message sets `PlayerState.typing`). Focusing players show an animated
  timer bubble.

### Travel, camera and minimap

- Moving between worlds closes an iris on you (honey rim), shows "Heading to …" with your
  character walking among clouds, and opens once you've arrived (at least 0.8 s, at most 9 s

- Zoom: +/− buttons or the mouse wheel adjust the automatic zoom by up to −2/+3 steps (kept per

- In homes, the interior now sits 40 tiles from the yard so it never peeks into view.

- While focusing: the verified timer is a ring (bottom right), the screen edges dim and the

## Phones and tablets (2026-10-28)

- Touch play uses a floating joystick: a thumb anywhere on the world steers, in eight directions
  (straight sectors are wider than diagonal ones so walking a path doesn't drift). It feeds the
  same input vector as the keys, so movement, prediction and the server's speed check are
  unchanged. Two fingers step the zoom like the zoom buttons. Taps still reach the game.
- "Press E" prompts are buttons, so a tap does the same as E (sit and focus, enter the shop).
  Doors and the garden gate already worked by walking into them.
- Whether the player is on touch follows the last pointer used (a coarse pointer at first), so
  hints and placeholders show taps or keys accordingly, including on laptops with touch screens.
- Decorating by touch: tap an item and then a spot, or drag; tapping placed furniture picks it
  up and a drag moves it; dragging empty ground pans the view, because a phone shows only part
  of the yard and the player can't walk while decorating. "Put back" replaces right-click/Esc.
- Focus verification is unchanged: touches count as input like keys and the mouse. A phone
  that locks hides the page, so those minutes don't count; the game holds a screen wake lock
  during a session (where the browser supports it) so the screen stays on.
- Layout: under 1240px the home bar moves below the HUD; on phones (under 700px wide) the
  toolbar folds into a menu button and drawers become bottom sheets; short landscape screens
  trim the bottom stack and let tall panels scroll. Page zoom is off (pinch zooms the world).
- A web app manifest and icons (`tools/art/app_icons.py`, built from the favicon) let players
  add it to the home screen and play full screen.

## Working in other windows (2026-11-01)

- Deviation from the brief (SPEC, focus rule 3): a minute no longer needs the tab to be visible.
  The point of the app is to work, and people work in other windows. "Audio-only" is gone, since
  every session now behaves that way.
- The input rule also changed. The browser can't see keystrokes in other apps, so "no input for
  10 minutes" would have ended every real work session. It now only applies while the game window
  is in front and focused.
- That leaves "still here?" as the check on someone walking away, so it has to reach them: a chime,
  a system notification if allowed, the tab title, and the mini timer. Minutes keep counting for 5
  minutes after the question, then pause until it's answered, so a person glancing away isn't
  penalised and an empty room stops earning. This is weaker than before (someone can answer every
  25 minutes without working), which is accepted: the daily cap still bounds it.
- The mini timer uses Document Picture-in-Picture, which only desktop Chrome and Edge have. It's
  optional: elsewhere the timer simply keeps running in the background.
- Phones can't do this: they suspend background pages, so beats stop. The wake lock keeps the
  screen on instead, and the panel says to keep the page open.

## Mini-games (2026-11-01)

- Four games, each with its own generated map (`tools/art/build_games.py`) and a `game` room
  filtered by game: fishing, rafting, butterfly catching and treasure digging. The brief asked for
  fishing, rafting and at least two more; these two were picked to add something different
  (chasing moving targets, and deduction) with art the pack already has, and all four work with
  one action button, so they play the same on a phone.
- **Coins come from time played, not from scores.** The server watches each minute, and one with
  at least 3 real game actions pays half a focus minute through `award_play` (same streak
  multiplier, so exactly half at any streak). Scores are only for show, so nothing a client claims
  can turn into coins, and a cheating client gets no more than an honest one.
- Paid play is capped at 120 minutes a day (the brief didn't ask for this): without a cap, games
  could quietly become the main way to earn, in a game about focusing. A minute doesn't pay while
  a focus session is running in another tab, or in an older game tab.
- All input is one `game:use` intent; the server decides what it means from the player's state. A
  raft is an ordinary player whose moves are checked against the water at raft speed, so banks and
  rocks are as solid as walls, and run times come from positions the server already accepted.
- "Up" paddles against the current, because a raft that could only go downstream could be stuck
  for good in a pocket between a rock and the bank.
- Scores last for the visit; nothing about them is saved. Bests and leaderboards can come later.

## Town Builder (2026-11-16)

- The tile editor was replaced by a piece-based builder, because moving a building meant
  selecting the right rectangle across six layers. Now the town is a layout of pieces (a
  building, a group table, a tree...) on painted ground, saved as
  `tools/town-builder/town.layout.json`. Saving compiles it into exactly the files the game
  already loads, so the game, the server and the map format are unchanged.
- That makes the layout the source of truth for the town, and `town.json` a build output of it
  (it was the other way round: CLAUDE.md said the map JSON was the source of truth after the
  generator). Hand edits to `town.json` are lost at the next save from the builder.
- Pieces come from `tools/art/build_town_kit.py`, which also wrote the starting layout: the town
  `build_town.py` made, rebuilt from pieces (the scattered trees differ, and two flower benches
  moved up a row because they overlapped the group tables).
- A piece claims only its footprint (its solid cells, or its bottom row), so pieces can't stack
  but tree tops and roofs can overlap what's behind them, as before. Fully transparent tiles
  of a picture are no longer solid.
- Desks get their names on save (`desk-1`...), and a group table or café row becomes one shared
  Pomodoro (`table-<piece id>`). The tree and animation sheets always hold every tree and
  animation in the kit, because the world map draws some of those trees too.
- The saved map carries a version, and the game adds it to the tileset and sheet URLs: those
  files keep their names when the town changes, and with day-long caching an old tileset under
  a new map would scramble the town.

## Introduction, shop sign and pinches (2026-11-16)

- New players get a six-step introduction the first time they're in the world (walking, focus,
  decorating, friends, games). `profiles.tutorial_seen_at` remembers it per account, set through
  `finish_tutorial()` as soon as it's shown, so closing the tab halfway doesn't bring it back;
  the "How to play" button reopens it any time. Existing players see it once too.
- A bobbing "Buy furniture here!" bubble sits over the Furniture Shop and gives way to the
  "Enter" prompt at the door.
- Friends can pinch each other: `pinch` is an intent with the friend's id; the server checks the
  friendship in the database, that they're online, and rate limits (one pinch every 3 seconds,
  the same friend every 20), then tells every tab they have open, in any room. They get a popup
  with "Pinch back", and a system notification if they're in another window.
- Who's online is a list in the game server's memory, filled as players join rooms. It's only a
  convenience (the friends panel's dots and pinches); after a restart it fills up again as
  players reconnect. Pinches to offline friends aren't stored.

## Game maps in the Town Builder (2026-11-16)

- The builder edits the four mini-game maps as well as the town (a picker at the top). Their
  layouts live next to the town's in `tools/town-builder/maps/`. The starting layouts were
  recorded by `tools/art/build_games.py --layouts` from the maps it had generated; trees at the
  very edge were nudged a tile in so their trunks are on the map, and the lake's arrival point
  is kept clear of trees.
- What the games read is worked out on save rather than placed by hand: fishing spots are every
  walkable tile beside water, the treasure dig zone covers the reachable sand, and a raft floats
  on water away from the bank and through no solid piece. The few things that need a decision
  are pieces: the Raft launch, the Finish line, Bonus buoys and a Place name.
- Each game map now has its own tileset (`tilesets/<map>.png`, loaded by map version like the
  town's) instead of one shared `tilesets/games.png`, so saving one map can't change another's
  tiles. The shared `sprites/games.*` holds every animation in the kit plus the raft and shells.
- On game maps, trees are tiles (the canopy drawn over players), as `build_games.py` drew them;
  only the town draws trees as swaying sprites.
